# Independent exact-prefix experiment

This worker independently runs a tokenizer-only experiment on all 22 fixed generation-diagnosis cases. It loads the existing local tokenizer with `local_files_only=True` and `trust_remote_code=False`, never model weights or MLX. It compares actual user-first ranker prefixes with stable catalog-first prefixes, records exact longest common prefixes and SHA-256 identities, and exercises the existing native append-boundary guard for baseline and manifest suffixes on both prefix layouts. All outcomes are retained in `PREFILL_ANALYSIS.json`.

```sh
.tools/pretrained-venv/bin/python -m unittest experiments.ranker.pretrained.test_prefill_analysis -v
.tools/pretrained-venv/bin/python -m experiments.ranker.pretrained.prefill_analysis --model /absolute/pinned/local/tokenizer-snapshot
```

The experiment also changes each public profile/task and clears history: the catalog key must stay unchanged. Changing a candidate's availability must invalidate the catalog key. These are actual token/key calculations, not cache speed estimates. Exact common leading chat-template tokens do not make complete state interchangeable. The native full-state serialization and A→B→A hardware tests belong to the existing cache proof; this CPU experiment does not rerun or replace them.

`catalog_cache.one` computes the user-first trained ranker prefix, discards its native state and separately prepares the catalog-first decoder cache. `generation_diagnosis.run_arm` does the same for its cache-source cases. Its evidence-source cases retain the ranker state, just as `evidence_plan.infer_arm` already does. That evidence path is the implemented valid same-context reuse: one complete native hybrid recurrent/convolution/KV state, exact suffix append, one decoder continuation, no splice, trim, speculative fork or cached response.

Replacing a catalog-first cache with a retained user-first ranker state changes context order and prompt identity. It is therefore a proposed decoder-context-layout intervention, not an equivalent cache-only optimization. The current bound calls for no new GPU run: the evidence path already demonstrates exact same-state reuse. A later comparison would need independent full quality and latency measurements; token tests cannot establish equivalent logits or wording for different prompts.

The result includes actual paired stage costs and token sums from `generation-diagnosis-v1/benchmark-reviewed.json`, with its source hash. Each scale has baseline/manifest and cold/warm catalog arms, plus existing evidence-arm comparisons. Logical input work counts ranker plus separately prepared/reused catalog plus suffix; fresh prefill tokens exclude the catalog on a hit. Full timings include head prefill, catalog materialization, generation and validation. Nonoverlapping accounting uses structured time + catalog preparation + prompt preparation + generation + validation, retaining the residual synchronization/audit cost. `nativePromptMs` overlaps first-token timing and is never added twice. No percentile subtraction or fresh timing claim is made.

Measured cold catalog preparation is about 1.34–1.38 seconds, including about 1.27–1.29 seconds of actual catalog forward work. Warm preparation is about 52–62 ms. The approximately 1.94-second ranker forward remains in both cache arms; removing a separate warm catalog load cannot be described as eliminating that ranker cost. Manifest output lengths and accepted fields differ from baseline, so their complete-latency differences are not a cache-only speed attribution. These are synthetic local experiments, with no production performance, human conversion or novelty claim.

A future batching proposal remains deferred. Read-only inspection of the installed `mlx_lm/generate.py` confirms `BatchGenerator.insert` accepts per-sequence caches, maximum output tokens, samplers, logits processors and stop sequences. This API availability alone does not establish that a shared hybrid prefix can be safely aliased across rows or that parallel card generation improves quality. Any later bounded comparison would require independently materialized complete native states, A/B parity with unequal suffix lengths and early finishes, and full materialization, memory, assembly and validation costs. No batching, GPU test or decoder change is part of this experiment.
