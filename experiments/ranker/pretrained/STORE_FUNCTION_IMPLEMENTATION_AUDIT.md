# Actual-store adaptation implementation review

CPU pre-native review found **no evaluation-target leak, TRAIN-mean leak, or false seven-attribute compatibility claim** in the candidate. The proposal is suitable for a future **known-catalog quality/component experiment**, subject to the execution gates below. No actual-store native feature extraction or fitting was performed in this audit or established by CPU tests.

One material timing gap remains: `run()` extracts all 64 features, closes the native encoder, fits the heads, and later loads stored query features for predictions. Fresh query native timing, warm16 cache reads, and head/guard timing are measured in separate phases. This does **not** measure an actual fresh-query → verified warm16 loads → learned head → guards/top-k request endpoint. These values must not be added and described as a measured request latency. The parent and candidate owner chose to preserve a components-only version at the migration boundary, with an explicit limitation, rather than restructure native lifecycle in this session.

A future reviewed lifecycle can keep the 64-forward budget: encode16 catalog +32 TRAIN requests, freeze the TRAIN extraction receipt, fit with the model resident, then encode each of16 EVAL requests freshly and immediately perform warm16 verification/head/guards under one actual timer. Freeze all model/control predictions before reading evaluation labels. That is a follow-up design, not an implemented or measured result.

Observed implementation boundaries:

- `request_text()` accepts only query, preferences, itemBudget, and hardRequirements. It rejects extra target/provenance fields. Product text includes public name/category/itemPrice/searchTerms, declared colors, and honest capability limits. IDs, scenario/persona metadata, images, routes and target labels are excluded.
- `build()` separates public cases from external labels. Evaluation text was independently supplied in `store_function_eval_v1.json`; all16 classes/products are intentionally TRAIN-seen. `read_public()` byte-hashes evaluation-label files for integrity but does not deserialize their targets. The runtime first parses those targets after writing `PREDICTIONS_FROZEN.json`.
- `fit_inputs()` selects exactly32 TRAIN query features and16 catalog features before loading numeric values. Only those define role means and labels. Mean member lists and tensor hashes are saved. Evaluation feature roundtrip verification during extraction is integrity work; their numeric values do not enter optimization or means.
- `FunctionHead` has two real 4096→16 linear role heads, 131,104 trainable parameters, and train-only centered/normalized features. The loop computes query and catalog cross-entropy, backpropagates and steps AdamW for80 fixed steps. The independent unconditioned prior has its own80 steps; the random head remains untrained. CPU review establishes this code path, not native training success.
- Checkpoint save/reload uses exact metadata, checksums, strict state shapes, finite values and exact tensor parity. `predict()` accepts no labels, returns all16 scores/full rankings, and computes learned/prior/random/permuted-query arms before evaluation labels open. The postfreeze oracle is explicitly nonlearned and nonserving. Query permutation changes class for every TRAIN and EVAL row.
- Eight paired evaluation requests hold task/catalog/guards fixed and change only one observed preference; all16 target classes occur once. Counts are32 TRAIN,16 EVAL,8 EVAL pairs,16 actual catalog products and64 native B1 inputs. Top1/top6 are the measured readouts. No top24, image, copy, complete page, hidden-history or conversion claim is established.
- Deterministic guards use inclusive item price, exact declared category/color, and fail closed on unsupported stock/size requirements. Eight fixed CPU guard probes are separate from the unconstrained learned quality cases. Hard category/color matching is exact text matching; it does not establish learned natural-language requirement extraction or exact later image/variant action binding.

The candidate owner's nine CPU tests passed in the parent's combined31-test run. Tests cover heldout mean membership, external-label input exclusion, finite types/scores, unsupported hard requirements, exact checkpoint reload, no-label prediction APIs, immutable data hashes and all eight guard probes. This audit read the implementation/tests and did not repeat the combined suite or execute native work.

Before any future native launch, require:

1. Exact final source/data/token packet hashes, current storefront-source freshness, reviewed local model path and full shard/tokenizer/config verification, serialized root ownership and no other GPU worker.
2. Actual64 B1 receipts, complete whole-input tokens with no truncation, active and observed peak≤6 GiB, and explicit postforward/final elapsed guard. The reviewed extraction loop currently checks its180-second guard **before** each call; a last call could finish beyond that limit without the next precheck.
3. A fixed-denominator failure artifact with completed forward/case counts if interrupted or failed. The reviewed runner currently preserves partial immutable features and does not write a completed report on failure, but lacks a dedicated FAILED/count receipt. Partial extraction cannot be promoted.
4. Actual80 learned updates and80 prior updates, finite losses/state, exact checkpoint reload, TRAIN mean receipts, fixed32/16 quality denominators and8 paired controls. Preserve all failed cases and do not tune fit steps from these results.
5. Recheck saved feature/head/prediction source integrity, full16 scores, hard guard compliance and shortfalls. Keep timing as separate components unless the lifecycle gap is separately implemented, reviewed and measured.

These are remaining native-evidence/receipt requirements; no automatic review denial occurred. The narrow learning claim is adaptation to the real16-product catalog using manually authored public-function supervision. One catalog example per class and class-correlated name/price prevent an unseen-product or nuisance-decorrelation claim. Arbitrary unmatched intent has no validated abstention threshold. The prior frozen seven-factor head is explicitly declared incompatible rather than silently reused.
